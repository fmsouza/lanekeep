# 0005 — Dual licensing, public development, registry publishing

**Status:** Accepted
**Date:** 2026-07-31

## Context

lanekeep is intended to be adopted inside corporate codebases and to accept rule contributions
from outside the project. Both depend on choices made before the first release.

## Decision

**License:** `MIT OR Apache-2.0`, at the user's option.

**Visibility:** public from the first commit.

**Distribution:** published to crates.io and npm from the first release, plus a Homebrew tap
generated by cargo-dist. npm is the primary channel — platform packages with a thin wrapper that
execs the correct binary, the pattern esbuild, swc and Biome all use.

## Rationale

Dual licensing is the Rust ecosystem's convention — rustc, tokio, serde and ripgrep all use it —
and it is effectively expected of a crate. Apache-2.0 supplies an explicit patent grant that
corporate legal review looks for; MIT stays available for those who find Apache-2.0 heavy.

Public development is a precondition for most of the project's stated goals rather than a
preference: free unlimited Actions minutes, branch protection at no cost, OpenSSF Scorecard, SLSA
provenance attestations, and rule contributions by pull request. An open source license on a
private repository is a contradiction.

npm is primary because lanekeep's users are TypeScript and JavaScript developers who already have
a package manager in the project. With no in-process plugin host there is no reason to ship a
native addon; the wrapper only needs to exec a binary.

## Consequences

- Contributors must accept dual licensing. Stated in `README.md` and `CONTRIBUTING.md` using the
  standard Rust formulation, so no contributor licence agreement is needed.
- Development happens in the open from before the tool works. Mitigated by an explicit
  early-development notice in the README.
- Names on crates.io and npm are claimed at first release and are effectively permanent —
  crates.io does not permit deletion after 72 hours. `lanekeep` was verified available on
  crates.io, npm and Homebrew before this decision was taken.
- Publishing requires `CARGO_REGISTRY_TOKEN` and `NPM_TOKEN` as repository secrets. Until they
  exist, release workflows run in dry-run mode.
